01

整条链路

三条输入在「SAS 特征流水线」处合并，合并点之后没有任何分叉——这就是仿真结论能迁移到真实录音的原因。

A

仿真与录音：给非技术读者的验证入门

一句话：仿真是在电脑里“造”一段座舱声音；录音是拿真实扬声器和麦克风“录”一段。两者最后喂给同一套检测算法，区别只在声音从哪来。

A.1 先理解原理

扬声器循环播放一段人耳几乎听不到的 Kasami 探测音（20 ms 一周期），麦克风同时听到“直达声 + 车内反射声”。有人呼吸或轻微移动时，反射路径会变化，接收到的“声学指纹”（CSI）随之起伏；系统从这些起伏判断：有没有人、有没有呼吸、是否持续不动。

A.2 仿真验证：不用任何硬件

适合先确认“算法和界面是否正常”。打开 http://127.0.0.1:8090，四步即可：

  1. 左侧选一个场景，例如「入睡婴儿」，点「开始监测」。
  2. 把倍速调到 8×，观察状态是否从「监测中」→「检测到儿童」→「告警」，呼吸率是否接近场景真值。若先在侧栏点「执行空车标定」，下次启动会加载该基线。
  3. 看曲线、事件流、座舱示意是否同步变化；点「暂停 / 停止」或「确认静音」验证交互。
  4. 在「日志回放」里选一条示例会话，拖动进度条复盘。
场景观察重点
空车厢全程不报警
入睡婴儿约 9 s 确认，10 s 预算内报警，BPM 稳定
活跃儿童运动证据先触发，呼吸率仍可输出
呼吸暂停先正常报警，呼吸停止约 15 s 后升级 APNEA
新生儿弱反射、30 BPM 也能检出
噪声振动有干扰但不误报
成人14 BPM 慢呼吸可测

也可以用命令行批量核对：

python3 replay_audio.py --selfcheck # 仿真 → WAV → 再回放，验证音频前端 python3 -m pytest tests -q # 70 项自动测试
仿真的特点：完全可控、可重复、16× 加速，几分钟就能跑完几个场景；缺点是声音模型理想化，没有真实混响、扬声器失真和复杂人际干扰。

A.3 录音验证：需要真实扬声器 + 麦克风

目标不是“录一段车内声音”，而是一边播放 Kasami 探测音、一边把声音录回来。没有 Kasami 探测音，系统拿不到 CSI。

  1. 准备硬件：车载音响或宽频音箱（尽量覆盖 14–20 kHz）；采样率 ≥ 48 kHz、频响 ≥ 24 kHz 的麦克风；麦克风固定，不要手持。
  2. 生成 Kasami 探测音并循环播放：用下面的命令生成 probe.wav，在车内持续播放。
  3. 不需要空车静置：系统开机第一帧就监测。可以先在空车厢里执行一次标定并保存基线，之后每次启动直接加载；不做标定则用开机前约 2 s 自适应估计背景。
  4. 录音 40–60 s：用 Audacity 或手机专业录音 App，输出 48 kHz、16-bit PCM WAV；关闭降噪、回声消除和自动增益。
  5. 分析并可选存档：跑检测，或存成会话后到 Web UI「日志回放」查看。
python3 replay_audio.py --emit-probe probe.wav --seconds 300 python3 replay_audio.py capture.wav python3 replay_audio.py capture.wav --save data/sessions

结果怎么读：看首次确认时刻、告警时刻与响应时间、呼吸率、补齐/空洞、削波样本。削波必须为 0；空车厢误报多半是未做空车标定、开机前 2 s 有人在动，或开了 AGC。

伦理边界：真实录音验证请用成人志愿者或呼吸模拟装置，不建议用真实新生儿做测试；本样机也不包含真实新生儿大规模验证。

A.4 仿真需要的“座舱录音”在哪里？

这是最容易混淆的一点：直接仿真不需要任何录音文件。三种媒体来源对应三种用途：

验证方式声音从哪来是否需要 WAV是否预生成
UI 直接仿真程序每 20 ms 实时合成 CSI不需要不涉及
--selfcheck七个仿真场景渲染成 WAV需要（临时）每次运行时生成到 data/selfcheck/，已忽略入库
真实录音真人/模拟装置 + 真实硬件需要需自己录制，仓库不提供

data/sessions/ 里的示例会话保存的是 CSI 与决策日志（frames.jsonl / events.jsonl / meta.json），不是录音，用于回放和事后复盘。

A.5 仿真和真实录音的核心区别

维度仿真真实录音
声音来源程序生成的多径模型真实扬声器播放 + 真实座舱反射
“儿童”来源参数化呼吸 / 动作模型成人志愿者或呼吸模拟装置
干扰预设噪声、振动突发空调、路噪、说话、开关门、多人活动
可重复性完全可重复，换种子可造差异每次现场条件不同，难完全复现
速度可 16× 加速必须实时录，一次至少 40–60 s
主要用途验证算法逻辑、UI、报警时序、回归测试验证真实频响、混响、时钟漂移、安装位置
能证明什么“逻辑是对的、参数是自洽的”“在这套硬件和这个车里能工作”
不能证明什么真实硬件上一定有效量产可靠性、所有车型 / 所有儿童都有效
正确顺序：先用仿真和 --selfcheck 把链路跑通，再做真实录音。仿真回答“算法对不对”，录音回答“换到真实世界还灵不灵”；录音通过也不等于量产通过。当前录音前端只完成过“仿真 → WAV → 回放”的闭环，尚未接真实扬声器/麦克风，这正是下一阶段要补的工作。
02

仿真输入是什么

不是音频，是参数。每个场景 = 一个「物理场景参数包」，由合成器算出理想 CSI。

输入项取值对应物理量
static_delays0.58 / 1.7 / 2.8 / 3.9 / 5.1 / 6.4 / 7.9 / 9.2 ms8 条座舱多径的往返延时
static_gains1.0 → 0.15 递减 + 随机相位各路径反射强度
noise_sigma0.020 – 0.022底噪，约合 35 dB 信噪比
target.enter_t / distance_m0.0 s / 1.35 – 1.55 m目标何时出现（七场景均为开机即在车内）、离话筒多远
target.bpm / chest_mm14 – 30 BPM / 3.0 mm呼吸频率与胸壁位移峰值
target.reflectivity0.030 – 0.045目标反射系数，决定回波强度
motion_events0.09 – 0.18 m / 1.0 – 1.6 s肢体动作幅度与持续时长
noise / vibration_bursts×2.6 幅度 / 3.4 s噪声突发、座椅振动

合成器每 20 ms 算一次下面的式子，再叠加复高斯噪声，取模后就是那一帧的 24 个数：

H(f, t) = Σr ar(t) · exp(−j2πf·τr(t))　　然后 |H(f, t)| 送入流水线

一帧 24 个子载波、每秒 50 帧。呼吸让 τ_target 以毫米级缓慢起伏，肢体动作让它在几十毫秒内跳变——两者在统计量上的差异，就是整条算法要抓的东西。

关键点：仿真输入里没有「波形」这个概念。波形只存在于路径 ② 和 ③，是前端处理的对象，而不是算法的输入。 所以「仿真能不能替代实录」这个问题的答案很明确：不能替代真实环境，但能证明算法本身和前端实现没写错。
03

三条路径各证明什么

覆盖范围是逐层叠加的：算法 → 音频前端 → 真实环境。每往上一层，能排除的错误类型就多一类。

PATH A

仿真直连

证明：算法逻辑对不对

  • 跳过音频层，直接给 24 个子载波振幅
  • 用于调阈值、看误报漏报
  • 跑得最快，7 场景约 30 s
run_offline(key)
PATH B

仿真 → WAV → 回放

证明：音频前端有没有写错

  • 渲染成真实 48 kHz 波形再解回来
  • A 与 B 的差 = 前端的引入误差
  • B 复现不出 A，说明前端有 bug
replay_audio.py --selfcheck
PATH C

实录文件

证明：真实座舱能不能用

  • 混响、扬声器非线性、麦克风频响
  • 只有这条能产出对外可引用的数字
  • 目前尚未跑过
replay_audio.py capture.wav
04

音频前端在做什么

从 WAV 到 24 个子载波振幅，中间五步。这里是整套实现里最容易出错、也最值得看的一段。

三个曾经踩过的坑

坑错在哪正确做法
用时域相关估 CSI CIR 被 Kasami 自相关主瓣（一个 78 µs 码片）糊成方块，时域反卷积在多径旁瓣与高端载波上都留误差 频域正则化除法 H=R·S*/（|S|²+ε），周期卷积在 DFT 网格上精确成立
载波不在 DFT 网格上 多径条纹间距约 150 Hz，网格 50 Hz，插值等于采样一个在两格间振荡的量，零噪声下也有 10% 误差 取整频点。无噪误差降到 1e-6，40 dB 下 0.5%
探测带边缘压在最外侧载波上 Kasami 的带限过渡带正好落在最外侧载波，探针功率被削掉，该载波退化成噪声计 两侧各留 200 Hz 余量（10.3–23.7 kHz），再逐载波功率均衡，带内功率差 < 3 dB
这三个坑都不是「调参能救」的。它们错在原理层，现象是「怎么调阈值都不对」。 如果只跑路径 A（仿真直连），这三个 bug 一个都不会暴露——这也是为什么路径 B 必须存在。

06

实采录音接入

五步：生成 Kasami 探测音 → 现场播放并录制 → 录音质检 → 命令行判定 → 存成会话。检测代码一行不改，只把输入从「仿真信道」换成「你的 WAV」。

① 生成 Kasami 探测音（只做一次）

# 48 kHz / 20 ms 一周期 / 10.3–23.7 kHz / 255 位 Kasami 码片扩频 $ python replay_audio.py --emit-probe probe.wav --seconds 300 # 60 s ≈ 5.8 MB，300 s ≈ 29 MB；循环播放即可，不要变速
这是主动探测，不是「录一段座舱里的声音」。没有 Kasami 探测音，麦克风收到的只有语音和路噪， 里面不存在任何 CSI 可反演的东西，程序会直接拒绝（no probe repetition found）。 探测音必须循环播放并原速原采样率输出，任何变速都会让 20 ms 栅格对不上。

② 现场录制

项目要求为什么
编码WAV + PCM 整数（16/24/32-bit）浮点 WAV 与 mp3 / aac / m4a 读不了，先转 16-bit PCM
采样率≥ 48 kHz最高载波 23.5 kHz，Nyquist 需 47 kHz。44.1 kHz 会被明确拒绝
声道单声道优先，双声道自动下混只用 |H(f)|，两声道相位差无意义
时长≥ 20 s，建议 40 s 以上不需要安静校准期；建议至少 20 s 有效证据（8 s 呼吸窗 + 5 s 证据窗 + 10 s 预算）
电平峰值 0.1–0.9 满刻度，不要削顶幅度统计对整体增益不变，但要避开量化噪底与削波谐波
1

关掉所有音频前处理

降噪、回声消除、AGC、波束成形，全部关闭。AGC 的人为幅度调制比呼吸引起的幅度变化大两个数量级；降噪会把 10 kHz 以上的 Kasami 探测音当噪声删掉。

2

不需要空车静置 5 s

检测器开机第一帧就监测。更稳的做法是先在空车厢执行一次空车标定（侧栏按钮或 POST /api/calibration），把该车该硬件的背景能量与相干门限存到 data/calibration/empty_cabin.json；未标定时用开机前约 2 s 自适应估计背景。两种方式都不要求先等安静期。

3

麦克风固定，不要手持

手抖在 10–30 cm/s，正好落在论文指出的 J0 零点速度带，是这个方法天然的盲区。把它夹在座椅靠背或支架上。

4

播放与录音同采样率、同速率

同一台设备最稳。跨设备允许缓慢漂移（帧同步按实测周期跟踪），但不能重采样或变速——慢放 8.8% 就会因匹配质量不足被拒。

5

记下距离、座椅位置、车窗、空调档

这几个变量决定结果能不能复现。同一台车同一个座位，换个空调档位，残差底噪就可能翻倍。

空车标定（运行时不强制，部署推荐做一次）

空车标定不是每次上电都要做的步骤，也不是“先安静 5 秒才能检测”。它是一次性的离线准备：用空车厢测出本车本硬件的稳态背景，之后每次开机直接加载。

方面说明
作用得到背景残差能量 δ₀ 与子载波相干门限 θ_κ，避免每次开机前 2 s 的冷启动估计被关门、人员走动或空调变化污染。同一车厢条件下确认更早，也不受当次开机瞬态影响。
方法空车厢、关门关窗，空调/音响按常用档位；停止当前监测；点侧栏「执行空车标定」、调用 POST /api/calibration，或运行 python3 -m core.calibration --simulate（仿真）/ --wav capture.wav（真实录音）。默认 5 s（允许 3–30 s），前 1 s 作 warmup 丢弃，实际用后 4 s 的 40 个决策帧。hw_f_max 省略即论文频带。
统计能量取样本 p35；相干门限取 p25 + 5.5×MAD，并夹在 [0.115, 0.22]。灵敏度旋钮仍在运行时按比例缩放运动阈值。
产物与加载写入 data/calibration/empty_cabin.json（已 gitignore）；下次 /api/live/start 自动加载。侧栏或 GET /api/calibration 可查看数值。
失效条件换硬件频响上限（20k/18k/16k/14k）或换车后应重标。载波数不匹配时加载会自动回退到冷启动，不报错；监测运行中调用会返回 409。
$ python3 -m core.calibration --simulate --seconds 5 # 实采空车录音（录音时必须循环播放 Kasami 探测音），--start 跳过开机/关门瞬态 $ python3 -m core.calibration --wav capture.wav --seconds 5 --start 1 --hw-f-max 18000 $ python3 -m core.calibration --show # 查看 $ python3 -m core.calibration --clear # 删除 # 也可走 HTTP：POST /api/calibration {"duration_s":5}；GET 查看，/api/calibration/clear 删除

为什么没有标定也能工作

系统不做空车回声相减：静态多径在 1 s 窗去均值 + 去线性趋势后已被移除，运动通道只看相对残差比 δ/δ₀，呼吸通道的 ACF 与 MRC 权重来自当前 8 s 窗。空车标定存的是归一化尺度与门限，不是相减模板。

没有标定时，δ₀ 取开机短窗残差能量的 p10、相干门限取 p25 + 5.5×MAD：低分位让“孩子已经在车内”时仍能用最安静的 10% 帧代表底噪。代价是默认开机前约 2 s 相对平稳——若孩子持续剧烈运动，δ₀ 被抬高，运动通道变钝，确认推迟到呼吸窗填满（约 9 s），但不会误报；若开机异常安静、随后噪声上来，运动证据会增多，30% 证据门限 + 相干性 + 干扰判据仍会拦住（stress 场景实测零误报）。

标定的价值是可复现：同一车队的基线固定，不受当次开机瞬态影响。实测活跃儿童加载标定后约 2.4 s 确认，冷启动约 9.0 s。所以“可选”仅指不阻断开机与检测，工程部署仍推荐做一次。

两种数据源不能混用。仿真基线（source: "simulation"）与真实录音基线（source: "wav"）的绝对幅度尺度不同：录音电平取决于播放与麦克风增益。因此仿真监测只加载仿真基线；检测到 WAV 基线时回退冷启动并在侧栏提示。
实采适配层已内置，不是“把 WAV 改名成 JSON”。空车录音必须包含 Kasami 探测音，--wav 会先由 core/replay.py 转成每载波复幅度（50 Hz），再按同一套统计计算；带宽、载波数与前端配置要和运行时一致。样机默认仍用仿真 empty 场景。

07

扬声器/麦克风到不了 20 kHz

硬件带宽不够时，失效不是「精度差一点」，而是「一半载波变成噪声源」。

论文的 10.5–23.5 kHz 假设了宽频换能器。车载球顶高音加 MEMS 麦克风常常只到 18 kHz，通话级器件甚至只到 16 kHz。这不是靠调阈值能糊过去的事，因为载波一旦落在硬件滚降上，该频点的探针功率接近零，谱除法就变成 噪声 / 噪声——估出来的 |H| 不再有信号成分，只剩一条宽带随机序列。

实测：硬撑 23.5 kHz 的后果

把现有 24 载波配置直接喂给 18 kHz 硬件（渲染 WAV 经 6 阶低通），空车厢的结果是：

载波位置相对抖动 std/mean后果
10.5–16.5 kHz（有效带内）0.013正常噪声底
21–22 kHz（滚降区）0.20 → 0.4815 倍于正常值，残差能量读到「运动」
空车厢最终判定确认存在并告警 BPM 报 12.7
这不是精度下降，是安全性崩塌。载波落在滚降上时，|H| 里根本没有信号成分，而残差能量与 MRC 权重没有任何办法把「噪声/噪声」和「有人动」分开。 所以必须让这些载波不存在，而不是指望阈值把它们压下去。

两条防线

防线 1 · 设计期

从硬件上限反推频带

plan_band(hw_f_max)

  • 载波带顶 = min(23.5 kHz, 上限 − 1.5 kHz)，离滚降留余量
  • 下限固定 10.5 kHz：三个档位的高通都是 10 kHz，这 500 Hz 就是它的余量，只有顶部随硬件移动
  • 载波数 = 带宽 / 250 Hz 封顶，保证相邻载波仍能去相关
  • 探测带随之收窄，不向发不出的频率送能量
  • 低于 12.75 kHz 直接报错（不足 4 路载波）；UI / API 只提供 14 kHz 及以上档位
防线 2 · 运行时

载波健康门控

SASPipeline 载波健康短窗

  • 开机后约 5 s 统计每个载波的相对抖动，剔除高一个数量级的那批；只裁载波，不阻断检测，也不要求座舱无人
  • 基准取25 分位而非中位数：一半频带死掉时中位数自己也会移进死载波
  • 存活不足一半则全部保留并报硬件异常，不悄悄在 3 路上继续跑
  • 界面仍显示死载波的原始幅度——那是硬件问题，不该被算法掩盖

连带必须改的一处：κ 阈值要随载波数缩放

秩一能量占比 κ 在 N 路上有接近 1/N 的零假设。载波从 24 降到 17 时，静窗中位数从 0.087 升到 0.113，原先固定的 +0.015 偏移让阈值落到 0.128，而持续噪声的峰值是 0.129——一声关门就能被确认成儿童。改成 median + 5.5 × 稳健σ 后：24 路仍是 0.115（行为不变），17 路升到 0.142，噪声峰值 0.124 被挡、真实运动最弱帧 0.185 仍通过。

以上是命令行路径。Web UI 侧栏也有「硬件频响上限」一栏，直接选档（论文 / 20k / 18k / 16k / 14k），选中即显示该档的频带、载波数与间隔；启动后下方「运行频带」显示实际值，运行时门控裁掉载波时会写成 24→23 路（已裁剪）。

先测硬件上限再配置，不要依赖兜底。不传 hw_f_max 时运行时门控仍能消除误报， 但载波是按 23.5 kHz 铺的，前端有效积分带宽被浪费，BPM 精度和运动灵敏度都吃亏。 测法：循环播放 Kasami 探测音（或 10–24 kHz 的宽带啁啾），用被测麦克风录回来做频谱，看 −3 dB 点在哪。

09

WebUI 的作用

它不在检测链路里——关掉它，检测照常运行。它的价值在「看清楚为什么判错」。

1

可视化内部量

调参时唯一能看到判错原因的地方：δ/δ₀ 曲线有没有越过 1.6、κ 是否低于门限、合并 ACF 上的呼吸峰长什么样、证据占比累积到多少、预算倒计时还剩几秒。这些量在日志里只是数字，画出来才能一眼分辨「是阈值太高还是峰值被干扰吃了」。

2

演示

16× 倍速下活跃婴儿约 1.1 s 出告警（加载空车标定后约 0.7 s），座舱声学动画 + 四张图 + 事件流同时推进。适合向非技术方解释这套东西在做什么。

3

日志回放

JSONL 会话可拖时间轴、1–16× 变速。呼吸暂停那条直接拖到 61 s 看 APNEA 升级，不用等仿真跑完。

注意两点：第一，界面跑的是路径 A（仿真直连），不读 WAV。实录音频要先 --save data/sessions 存成会话，才会出现在「日志回放」列表里。 第二，左侧「仿真真值对照」面板只用于验证，检测链路完全不读它。
10

已知限制

这套前端从未接过真实硬件。全部验证都是「仿真 → 渲染 WAV → 回放」的闭环。 它能证明前端实现没写错，但证明不了真实座舱的混响长度、扬声器非线性、麦克风频响、多人活动这些因素。 要拿到能对外引用的数字，必须先实采一批。

另外两点需要如实记录：

MRC 的分集增益仍未验证。mrc_neff 从 23.48 降到 14.96–21.87， 但仿真器的目标反射是频率平坦的（各子载波目标强度相同），权重分化只来自噪声实现。要验证论文的 MRC 贡献，必须引入频率选择性目标 RCS 与多径衰落。

BPM 精度只能内部看。0.21–1.96 的 MAE 跑在正弦呼吸的仿真信道上，没有真实婴儿的呼吸不规则性、体动伪影和多人干扰。

带宽受限的数字同样只有仿真支撑。第 07 节的 18/16 kHz 结论来自「仿真信道 + 理想 6 阶低通」， 真实器件的滚降形状、通带纹波、单元谐振峰都没有建模——真实 16 kHz 器件的可用带宽很可能比这里的 14.5 kHz 还窄。
